# Trakr 資安說明

## 先說清楚：這份文件不是「符合資安規範」的保證

沒有人能在開發階段替你保證系統「符合資安規範」。原因是：

- 合規是由**稽核或第三方驗證**認定的結果（例如 ISO 27001 認證、滲透測試報告、個資法律意見），不是程式碼本身能宣告的。
- 合規取決於**部署與營運**：主機怎麼設定、備份怎麼做、誰能接觸資料、出事怎麼處理。這些不在原始碼裡。
- 這個專案還在 MVP 階段，下面「尚未做到」列出的缺口，在正式上線前都必須補上。

這份文件能做的，是**如實說明目前已經實作了哪些控制、哪些還沒有、以及上線前該做什麼**，讓你能拿它去和資安顧問、律師或券商洽談。

## 1. 「只讀取、不下單」是怎麼被保證的

「唯讀」是這個產品最重要的承諾，所以我們用四層互相獨立的防線，不依賴單一機制：

| 層 | 防線 | 誰控制 | 狀態 |
|---|---|---|---|
| 1 | 券商 API 金鑰**不勾下單權限**，下單在券商端就會被拒絕 | 使用者與券商 | 靠使用者設定；文件與介面都有指引，但**無法由我們強制或檢查** |
| 2 | 同步程式用**白名單代理**包住券商 SDK：只有 `login`、`logout`、`stock_account`、`update_status`、`list_trades`、`list_positions`、`account_balance`、`settlements` 能被呼叫；其餘（包含任何下單、改單、刪單、啟用憑證、期權帳戶）在呼叫前就丟出例外 | 程式碼 | 已實作，有測試 |
| 3 | 同步程式**從不載入或啟用憑證（CA）**，原始碼中禁止出現下單與憑證相關字樣，並有測試掃描 | 程式碼 | 已實作，有測試 |
| 4 | **伺服器沒有任何下單功能**，也**從不接收券商金鑰**。同步程式只送出成交、庫存、現金與 Trakr 自己的同步金鑰 | 程式碼 | 已實作 |

誠實的限制：

- 第 2、3 層是**白名單加測試**，不是作業系統層級的沙箱。懂程式的使用者可以修改自己電腦上的同步程式，所以對「使用者自己」不構成防護，它防的是**我們自己的程式碼出錯**，以及**日後的修改被審查者發現**。
- 真正擋得住「別人偷到金鑰後下單」的是第 1 層。所以我們在產品流程中一再要求使用者不勾下單權限，並建議綁定 IP 與設定到期日。
- 白名單的設計是「新版 SDK 多了交易函式，預設一樣被擋」，要放行必須改程式碼，會出現在審查中。

## 2. 我們保存哪些資料

| 資料 | 內容 | 敏感度 | 對外公開？ |
|---|---|---|---|
| 帳號 | 電子郵件、帳號 ID（@id）、密碼雜湊（scrypt） | 高 | 只公開帳號 ID |
| 工作階段 | 登入 cookie 的雜湊 | 高 | 否 |
| 同步金鑰 | 金鑰的雜湊 | 高 | 否 |
| 券商帳戶指紋 | 券商代號加帳號的 SHA-256 雜湊 | 中 | 否 |
| 成交紀錄 | 股票、買賣、股數、價格、時間、券商單號 | 高 | 依使用者設定，延遲至少 3 分鐘 |
| 庫存快照 | 股票、股數、均價、現價 | 高 | 依使用者設定（完整／比重／隱藏） |
| **現金與總權益** | 用來計算報酬率與推算出入金 | **高** | **否**；對外只有以 1 為起點的報酬指數，不含金額 |
| 自行上傳的 CSV 交易 | 同成交紀錄，標記為未驗證 | 高 | 同上 |
| 社群貼文、留言、檢舉 | 純文字 | 低到中 | 貼文留言公開 |
| 大頭貼 | 256 像素的 JPEG 或 PNG 圖片 | 中（可能含人臉） | 公開 |
| 自我介紹與社群帳號 | 最多 160 字的純文字，以及至多 6 個社群**帳號名稱**（不存網址） | 低到中 | 公開 |
| 庫存快照（期初持倉） | 使用者上傳某日收盤的持股（代號、股數、可選均價）。Level 1，未經驗證；與後續成交的差異會記錄並列出；不進入券商驗證的排行榜，也不進入雜湊鏈 | 高 | 依使用者設定（完整／比重／隱藏）；比重模式下不公開股數 |
| 自選股 | 使用者關注的股票代號與加入時間 | 中（反映個人投資關注） | **否**，只有本人看得到 |

**我們不保存**：券商 API Key、Secret Key、憑證、身分證字號、銀行帳號。登入失敗次數與來源 IP 只存在伺服器記憶體中用於限流，重啟就消失。

## 3. 已實作的控制

| 領域 | 控制 |
|---|---|
| 密碼 | scrypt 雜湊與隨機 salt；長度 8 到 128；登入對「帳號不存在」與「密碼錯誤」回傳同一個錯誤並做等量運算，避免被用來探測哪些信箱已註冊 |
| 登入狀態 | 隨機 256 位元 session，只存雜湊；`HttpOnly`、`SameSite=Lax`，正式環境加 `Secure`；30 天到期；改密碼會登出其他所有裝置；JavaScript 讀不到 |
| 暴力破解 | 同 IP 加同信箱 15 分鐘 5 次失敗即鎖；單一 IP 15 分鐘 40 次；註冊每 IP 每小時 10 次 |
| CSRF | SameSite cookie，並拒絕 `Origin` 與請求主機不同的寫入請求 |
| 同步金鑰 | 隨機產生、只存雜湊、可隨時撤銷、每人最多 5 把；**只能上傳資料**，不能登入網站，登入 cookie 也不能用來上傳 |
| 資料完整性 | 成交紀錄只能新增、不能修改；以 SHA-256 雜湊鏈串接，事後竄改可被偵測；沒有任何手動新增或修改成交的端點 |
| 防造假 | 一個券商帳戶只能綁一個使用者；從綁定當下起算，拒絕補登更早的資料；庫存與成交不一致、交易時段內斷線都會移出排行榜 |
| 帳號 ID 唯一性 | 唯一性以**小寫鍵**判斷並由資料庫唯一索引強制，「Alice／alice／ALICE」是同一個 ID，擋下以大小寫變化冒名；僅限 ASCII 英數與底線，擋下西里爾字母等**外觀相同的字元**（例如以 `а` 冒充 `a`）；系統、職稱、券商與證交所名稱等保留字，以及 `admin`、`trakr` 開頭者不可註冊；兩人**同時**註冊同一 ID 時由資料庫決勝，落敗者得到正常的「已被使用」而不是伺服器錯誤；註冊後 ID 不可更改，沒有任何端點能修改；公開頁面不洩漏電子郵件、小寫鍵或內部編號；即時檢查端點每個 IP 每分鐘 60 次；舊資料庫升級時若發現僅大小寫不同的重複 ID，會**拒絕啟動並指出是哪些**，不擅自決定誰保留 |
| 輸入驗證 | 所有欄位檢查型別、範圍與長度；使用者輸入進入 SQL 時一律使用參數綁定（程式中唯一的字串拼接是固定的表名與常數）；貼文與 CSV 只當純文字處理，前端由 React 轉義輸出，不使用 `innerHTML` |
| 防狙擊 | 延遲公開由伺服器強制，下限 3 分鐘，使用者無法調低 |
| 快取 | 所有 API 回應帶 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer` |
| 內容安全 | 檢舉機制；同一內容被 3 位不同使用者檢舉即自動隱藏；發文與留言有頻率限制 |
| 圖片上傳 | 型別依**檔案開頭的特徵位元組**判斷，不信任使用者宣稱的類型；只收 JPEG 與 PNG（不收 SVG 與 GIF）；檢查宣告的長寬（32 到 1024 像素），避免「檔案很小但宣告超大畫布」拖垮其他使用者瀏覽器；檔案上限 200 KB、每人每小時 10 次；回應附 `nosniff`、`Content-Security-Policy: default-src 'none'; sandbox` 與 `Cross-Origin-Resource-Policy: same-site`；瀏覽器端裁切並重新編碼，移除 EXIF（含 GPS） |
| 簡介與社群連結 | **使用者從不提交網址**，只提交帳號名稱，由伺服器以固定範本與固定網域產生連結，因此不可能指向釣魚或轉址網站，也無法放出 LINE／Telegram 群組邀請（其路徑格式範本產生不出來）；貼上的網址會先驗證網域（擋下仿冒網域、`instagram.com@evil.com` 這類帳密寫法、非 https 協定）；簡介只當純文字顯示、不自動轉成連結；外部連結一律 `target=_blank`、`rel="noopener noreferrer nofollow ugc"`；每人每小時 30 次更新；3 位不同使用者檢舉即自動隱藏該人的簡介與連結（帳號本身不受影響） |
| 市場資料 | 只從證交所官方 OpenAPI 取得，不爬網頁（其使用條款禁止）；伺服器端統一抓取並快取 10 分鐘，使用者的 IP 不會送到證交所；上游失敗時顯示舊資料並標示，從不把錯誤格式當成空資料；每個畫面都帶授權要求的來源標示 |
| 測試 | 伺服器 74 個、核心 24 個、同步程式 8 個自動化測試，涵蓋以上多數控制 |

## 4. 尚未做到（上線前必須處理）

### 基礎設施與營運

- [ ] **HTTPS／TLS**：目前只有應用程式本身，沒有部署設定。上線必須全站 HTTPS 並啟用 HSTS。
- [ ] **資料庫靜態加密**：目前是本機 SQLite 明文檔。正式環境應使用有加密與存取控制的託管資料庫，或至少磁碟加密。
- [ ] **備份與還原演練**：尚無。
- [ ] **稽核紀錄**：沒有記錄誰在何時登入、撤銷金鑰、被檢舉內容如何處理。
- [ ] **安全標頭**：網頁本體（前端）還沒有 CSP、frame-ancestors 等標頭，要在託管層設定。
- [ ] **多台伺服器的限流**：現在限流存在記憶體，多台機器時會失效，需改用共用儲存。
- [ ] **反向代理設定**：必須設定 `TOT_TRUST_PROXY=1` 並正確轉發標頭，否則限流看到的是代理的 IP。
- [ ] **機密管理與監控告警**。

### 帳號安全

- [ ] 忘記密碼、電子郵件驗證（需要寄信服務）。目前**信箱沒有驗證**，任何人可用別人的信箱註冊；信箱的 Gmail 別名寫法（`a.b@gmail.com` 與 `ab@gmail.com` 實為同一信箱）也被視為不同信箱，可重複註冊多個帳號。
- [ ] **帳號 ID 無法更改，也沒有釋出機制**：刪除帳號功能還沒做，日後做時要決定 ID 是否立刻釋出或保留一段時間（立刻釋出會讓他人撿走舊 ID 冒名）。
- [ ] 保留字清單是人工維護的有限清單，無法涵蓋所有冒名手法（例如 `0fficial`、`trakr-` 以外的近似拼法）。
- [ ] 雙因素驗證或 Passkey。
- [ ] 若上架 App Store 且提供第三方登入，須同時提供 Sign in with Apple。

### 個資與法遵

- [ ] **隱私權政策與服務條款**頁面，載明蒐集項目、目的、保存期間、對外提供。
- [ ] **使用者行使權利的流程**：查詢、更正、刪除、匯出。目前沒有自助刪除帳號與資料的功能。
- [ ] **資料保存與刪除政策**：成交與庫存資料要保存多久、帳號刪除後怎麼處理。
- [ ] **資安事件通報流程**。
- [ ] **大頭貼審核**：目前沒有針對照片的檢舉入口、影像內容偵測或人工審核，任何人都能上傳公開可見的圖片。上線前至少要能檢舉與移除不當頭像。
- [ ] **簡介文字仍可能夾帶詐騙話術**：例如「加 LINE：xxx 帶你賺」寫在自我介紹裡，只是不會變成可點連結。目前只靠使用者檢舉（3 人自動隱藏），沒有關鍵字偵測、也沒有人工審核。投資類平台應優先補上。
- [ ] **EXIF 移除只在使用者端完成**：正常流程中瀏覽器會重新編碼並移除位置資訊，但繞過網頁直接呼叫 API 的人可以上傳帶 EXIF 的檔案（只影響他自己的隱私）。若要由伺服器保證，需要在伺服器端重新編碼圖片（會引入影像處理函式庫與其弱點面）。
- [ ] **證交所資料授權的長期風險**：授權條款允許機關在情況變更時停止提供資料；資料來源與授權文字應定期檢查。
- [ ] **內容審核工具**：現在被隱藏的內容只能手動改資料庫；也還沒有封鎖使用者功能（App Store 對使用者生成內容有此要求）。

### 供應鏈與驗證

- [ ] **滲透測試或第三方資安檢測**，並留存報告。
- [ ] **相依套件鎖定與掃描**：`npm audit` 目前回報 esbuild 有 2 個弱點（來自開發用的 Vite 伺服器，不進入正式環境，但仍應升級）。同步程式的券商 SDK 版本尚未鎖定。
- [ ] **同步程式的發佈**：目前是原始碼，沒有簽章、沒有可重現建置。使用者要信任它，需要公開原始碼並提供校驗碼或簽章。
- [ ] **Shioaji 轉接器尚未對真實或模擬帳戶測試**，現金與交割款的算法可能有誤，會直接影響報酬率正確性。

## 5. 需要律師或顧問確認的事

我不是律師，下列只是「該去問的問題」，不是法律意見：

1. **個人資料保護法**：成交、庫存與現金屬於個人財務資訊。蒐集的告知事項、同意方式、委外與跨境儲存（雲端主機位置）、保存期限與當事人權利，需要法律意見。
2. **證券投資信託及顧問法**：向不特定多數人提供個股推薦或分析，可能牽涉投顧執照。讓使用者分享自己的持倉與討論是否構成，要看實際內容與運作，請諮詢律師。目前產品有「不構成投資建議」聲明，但聲明不等於免責。
3. **券商的 API 服務條款**：使用者的帳務資料能否轉交給第三方平台展示，要看各家條款。**這可能直接決定整個產品能不能合法運作**，務必逐家確認。
4. **券商與金融機構的資安要求**：證券商本身受主管機關的資安規範約束；你不是券商，但若要和券商談正式合作（本專案的長期方案），對方通常會要求你提供資安與營運文件，常見的是 ISO 27001 驗證或同等的第三方評估。這些要求以對方提出的為準。

## 6. 出事時怎麼辦（使用者端）

- **同步金鑰疑似外洩**：在「我」頁面撤銷該金鑰。生效是立即的。
- **券商金鑰疑似外洩**：到券商 API 管理頁面刪除該金鑰並重建，並檢查券商帳戶近期委託與成交。若當初沒勾下單權限，對方無法下單。
- **懷疑帳號被盜**：變更密碼（會登出所有其他裝置），然後撤銷全部同步金鑰。

## 7. 上線前建議順序

1. 部署到 HTTPS、託管資料庫與加密、備份。
2. 用永豐模擬環境與小額實盤驗證轉接器，修正現金與交割款算法。
3. 補忘記密碼、信箱驗證、帳號刪除與資料匯出、隱私權政策與條款。
4. 補稽核紀錄、封鎖使用者與審核後台。
5. 升級有警告的相依套件，鎖定券商 SDK 版本。
6. 找第三方做一次滲透測試。
7. 請律師審視第 5 節的四個問題，並向各券商書面確認 API 條款。
